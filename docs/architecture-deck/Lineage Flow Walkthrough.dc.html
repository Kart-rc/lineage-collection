RUN TIMELINE r-102 · correlation c-55a1
QUEUED→CLASSIFIED→ANALYZED→RESOLVED→MERGED→PROPOSED→IN_REVIEW→PUBLISHED
Every stage transition is written to the run ledger; a failed stage is redrivable without re-running completed work.
WHAT MAKES IT CHEAP
Dedupe kills webhook replays at the door · determinant scoping keeps runs bounded · SCA cache serves unchanged (repo, digest, ruleset) without re-analysis · LLM cache serves unchanged chunks free · the interactive lane is never starved by this bulk traffic.
DETERMINANT BUMPS
The same machinery handles platform changes: a new ruleset, prompt, resolver or catalog snapshot version re-queues exactly the affected scopes — an auditable, bounded re-derivation instead of a big bang.

Union rules
• Idempotent: replaying any assertion N times yields one provenance entry (stable provenanceId) and a stable version.
• Commutative: arrival order across engines never changes the final record — proven in CI.
• Append-only: a provenance entry is never rewritten or deleted; decay marks stale after 3 silent cycles, never removes.
• Cross-repo stitching: when another repo reads daily_revenue and writes customer_features, the edge appears once both repos are analyzed — matched purely by URN.
When engines disagree
• Two exact/probable transforms whose normalized forms differ (canonical sqlglot trees) → CONFLICTING → review queue, all provenance intact — never averaged.
• SCA asserts WRITE but ≥ 3 COMPLETE runtime sessions covering that path observe nothing → CONFLICTING.
• Late arrival on a PUBLISHED edge (e.g. runtime evidence lands next week) → proposal v+1 through the normal gate — never a direct graph write.
• Absence is never negative evidence; an incomplete session never demotes.

STEP 7 · L09 → L10 → L11 — THE FENCED TAIL
How it gets published — and queried
Presents the component PRDs (L01–L16); every AWS path is AWS_REQUIRED until the approved ephemeral deploy and smoke workflow runs. Normative production AWS view: docs/architecture/lineage-platform-target.md
1 · APPROVE
Reviewer inspects provenance + diff, enters a rationale, approves proposal p-3301 v2. Server-enforced, audited.
2 · MANIFEST
Checksummed manifests/staging/v2.json: proposal version, reviewer, expected prior v1, full edge enumeration. Object-Locked.
3 · RESERVE + FENCE
Conditional DynamoDB lock; monotonic fencing token t=1. An expired or stale worker can never win.
4 · STAGE + VERIFY
Edges written into inactive namespace v2; counts + checksums verified against the manifest. Any mismatch → staging discarded, no swap.
5 · ATOMIC SWAP
One transaction advances the pointer iff reservation + token + expected-prior all match. staging: v1 → v2. Rollback = re-point, never rewrite.

WHY FENCING MATTERS
Two publishers racing? The loser's token is stale — its transaction fails and its staging is discarded. Split-brain is impossible by construction (property-tested + chaos-drilled). Version history is retained: pinned queries against v1 still answer.
WHAT USERS SEE (L11)
Every rendered edge shows band + mechanisms + evidence links — no bare edges, never more certainty than the band supports. Depth ≤ 5 traversal, version watermark on every response, and the dropped-column impact above turns into a PR-gate BLOCK — only ever from a HIGH/HIGHEST band, never from an LLM-only edge.
